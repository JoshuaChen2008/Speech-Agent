# 用户掌控的个人记忆：收益评估与设计建议

日期：2026-10-02。用户已批准实施，并选择独立配置的云端表征与保留应用内直接编辑。要求已先登记为 SEM-F41/F42、ADR0025 和 J21/J28-FILES/J22/J24-RETRIEVAL；实现与验证见[交付记录](validation/personal-memory-files-2026-10-02.md)，操作见[使用说明](personal-memory-guide.md)。以下收益分析保留为设计依据，以已接受的上述决定和语义合同为准。术语依据 [CONTEXT.md](../CONTEXT.md)。

建议采纳文件所有权方向，先建立 Markdown 正文、确认与撤销的一致性，再以同一个 `resolve` 接入词法与向量召回。向量默认是否开启，由本项目题集和用户电脑上的资源证据决定。已有[存储研究](research/personal-memory-markdown-storage-2026-10-02.md)与[文件所有权和混合检索研究](research/personal-memory-file-ownership-hybrid-retrieval-2026-10-02.md)作为背景，本文件进一步给出推荐默认行为、恢复边界和验收出口。

## 1. 收益是否值得承担改造成本

| 目标 | 对用户的收益 | 主要代价 | 判断 |
|---|---|---|---|
| 已确认个人记忆正文以 Markdown 为准 | 离开应用仍能阅读、纠正、整理和携带正文；应用不能用隐藏正文覆盖用户文件 | 文件与数据库不能共享事务，需要明确确认、冲突、删除和恢复协议 | 与本次诉求直接对应，优先实施 |
| 自选目录与外部编辑 | 使用已有编辑器、文件命名和备份习惯；用户控制文件位置和应用写入 | 目录暂时失联、编辑器替换保存、重复 ID、同步冲突都要显式处理 | 收益明确，但目录自选不能被解释为信任目录中所有内容 |
| SQLite 保留治理记录 | 继续解释来源、确认性质、修订、忘记、删除与阻止旧来源再生 | 治理记录不是缓存，需要独立携带和恢复规则 | 必须保留，否则会削弱现有确认与撤销能力 |
| 词法检索 | 项目名、简称、术语和编号更容易找到；不要求表征模型就绪 | 中文短词与范围过滤要专门设计 | 先建立可比较的中文基线 |
| 向量召回与词法融合 | 可能找回改写、同义表达和措辞不同的相关背景 | 模型资源、更新成本、误召回与资源竞争 | 值得评测，尚无本项目收益数值 |
| 索引可重建 | 索引损坏、算法或模型升级不要求改写个人记忆正文 | 重建期间覆盖不完整，需有明确降级与进度 | 应作为索引设计的前置条件 |

收益分两类：文件所有权改善用户控制，检索改善相关内容的发现。更换存储格式本身不证明模型答案更准确；两路召回也不保证在有限上下文预算内优于单路。当前没有本轮性能、内容质量或投入工时对照，不能给出实测提升比例。

## 2. 各层分别拥有哪种事实

| 内容 | 建议权威位置 | 派生数据与恢复规则 |
|---|---|---|
| 已确认个人记忆的当前正文 | 用户指定目录中的 Markdown | SQLite 可以记录引用与摘要，正文投影和索引不能独立修改或补回文件 |
| 确认、作用范围的已接受版本、来源、修订、休眠、忘记、删除与 suppression | 现有 SQLite，由 storage worker 单写 | 不能仅凭 Markdown 重建；文件中的 `confirmed` 等自定义字段不能授予确认或有效来源 |
| 自动提取的记忆候选 | 首片沿用现有 SQLite | 候选不因创建文件而升级为明确内容；用户确认后才提交对应 Markdown 正文 |
| 会话经历记录与正式 Agent 交互 | 沿用现有 SQLite | 仍是与个人记忆分开的事实，不复制成整场 Markdown 记忆 |
| 词法与语义索引、读取缓存 | 同库的受控派生数据，或有界内存缓存 | 从当前文件与有效治理记录重建，不能恢复确认、来源或撤销 |
| 个人记忆综合视图 | 沿用现有有界投影 | 当前与上版都受来源和修订失效约束，不成为另一份可独立修改的个人记忆正文 |
| 权威原始转写及字幕历史 | 沿用 SQLite 字幕事实 | 继续锚定首次 `final`，不受文件目录与任何索引影响 |

这里的“Markdown 权威”作用于已确认个人记忆正文，不将全部产品数据改为 Markdown。SQLite 回答“这份正文是否已确认、来源是否有效、现在是否允许引用”，不能回答“文件缺失时应恢复哪份旧正文”。正文权威和治理权威分工，不允许两个独立的正文写入分支。

“撤销”沿现有来源撤销、忘记、删除和 suppression 语义；不因此承诺数据库保留可恢复的全部历史正文。若以后提供正文版本恢复，应单独定义保留期限、用户动作与删除边界。

## 3. 推荐的目录、文件与用户操作

用户通过 main-owned 目录选择器选择一个记忆根目录，可以创建空目录或接入已有目录。接入时先列出范围和待确认文件，不自动将所有 `.md` 作为本人事实。根目录位置由主进程管理；renderer、模型与 recipe 只使用受控身份，不能提交任意文件路径。

首片默认一份文件对应一条个人记忆。文件名、标题和子目录由用户控制，身份不从路径推断。最少已识别元数据是稳定 `id`、既有七种 `kind` 中的一种及既有 `scope`；没有元数据的文件可阅读，并在用户确认加入时协助登记。不是要求用户手写数据库字段。

应用保留未知自定义字段、注释和排版，不对整份文件自动重排；没有用户明确动作不把文件内容改成另一种表达。超出已登记条目容量的文件仍属于用户，可阅读和编辑；应用提示拆分或选择内容，不静默截断后声称已经纳入记忆。Markdown 链接、图片和代码块不授予读取其它目录、执行命令或调用工具的权限。

“我的记忆”保留现有概览、候选、来源与编辑入口，并增加选择目录、打开目录、在外部编辑器打开、检查外部修改、重建索引和携带管理信息的操作。概览中的修改继续落到对应底层条目，不能把修改概览当作已修改全部记忆。

用户可以关闭应用对记忆文件的写入权限，继续外部编辑、查看和检索已经满足确认规则的内容。此时接受候选可返回可审阅的正文提案，由用户保存后确认；关闭写入权限本身不等于关闭个人记忆，个人记忆休眠仍按既有开关执行。

切换目录只更换本次读取的文件集合，不默默合并两个目录或将旧目录文件删除。将同一目录搬到新位置时保留稳定 ID 与治理关系；接入另一组文件时重新核对身份与摘要。首片不承诺跨电脑、多应用或云同步的并发合并。

## 4. 确认规则与外部编辑的推荐默认行为

| 发生的动作 | 正文与确认如何变化 | Agent 读取与依赖处理 |
|---|---|---|
| 用户在应用内明确添加、确认或纠正 | 确认绑定本次确切正文、kind、scope 和摘要；手动操作零模型调用 | 文件提交与治理登记达到一致点后，新的明确内容才可读取 |
| 外部修改正文、kind 或 scope | 显示文件当前内容，形成待确认的新修订；旧确认不能套到新正文 | 新修订在用户确认前退出 Agent 读取；不得回读旧数据库正文替代它 |
| 只重命名或在根目录内移动 | 稳定 ID 不变，正文身份不变 | 更新定位信息，不制造独立证据或新记忆 |
| 修改未被消费的自定义字段 | 原样保留；按固定解析规则判断实际消费内容是否变化 | 不因未知字段自行升级、撤销或扩展范围 |
| 新增或导入文件 | 先作为待确认文件展示，不信任其中的确认与来源声明 | 用户确认成为明确内容后再进入相应范围；不得伪造字幕或交互来源 |
| 同一个 ID 出现于两个文件 | 显示身份冲突，不按更新时间择优覆盖 | 两个冲突文件均不得进入 Agent 输入，直到用户解决 |
| 明确忘记 | 保留用户文件，SQLite 记录停止引用的事实 | 退出检索、关联与当前/上版概览；文件扫描不能自动恢复 |
| 明确删除 | 先登记撤销与各已登记历史身份/来源的 suppression，再按用户选择处理文件 | 即使文件删除失败或备份回来，也不得静默恢复有效记忆 |

外部编辑后逐条核对并确认当前正文、类型及范围；本轮没有批量确认。目录中的保存不自动代表本人确认。应用能发现文件改变，却通常不能证明写入者是用户本人、同步软件还是其它 Agent。这项产品取舍保留现有确认规则，同时允许用户直接掌控正文。

确认检查至少区分文件字节摘要与消费内容摘要：前者用于竞争写入检查，后者绑定实际进入 Agent 的正文、kind、scope 及固定解析政策。纯路径变化不改变确认，解析政策升级也不能偷偷放宽确认。旧修订对应的个人记忆会话关联与概览先失效，重建不能读取上版综合正文作为唯一事实。

自动提取仍先形成记忆候选，在原授权范围内低权重辅助；对已确认文件的外部修改则是待确认修订，不借候选通道自动改变当前明确值。候选确认后建立文件，自动推断只能补来源或提出冲突候选，不能覆盖用户正文。纠正后的新正文以用户操作为来源，原有字幕引用只能作为历史出处，不能冒充支持新措辞的原话。

## 5. 文件发现、写入竞争与跨介质恢复

文件监听只是变化提示。Node 官方说明 `fs.watch` 并非跨平台完全一致，Windows 上根目录移动或重命名可能没有事件；因此启动、恢复、显式刷新、实际读取和提交边界都需要重新核对。[Node 文件监听限制](https://nodejs.org/api/fs.html#caveats)

发现变化时先将相关旧修订标记为不得读取，再在有界队列中解析和登记新摘要。读取只接受稳定、完整且符合容量限制的文件；半写入、格式损坏、重复 ID 或读取失败都明确反馈。不能继续把过期索引当作当前正文。

根目录失联、权限错误与单个条目删除必须分开：

- 根目录无法完整读取时暂停该目录的上下文注入，不批量写 suppression，也不将所有文件解释为用户删除。
- 单个文件暂时缺失时先退出读取；只有根目录健康、稳定对账确认原 ID 确实离开所选目录后，才按已登记删除规则记录 suppression。编辑器替换保存与根内移动需通过有界合并及按 ID 对账处理。
- 同 ID 的旧文件重新出现不能取消已有忘记或删除；恢复必须由用户明确操作并检查当前正文和来源。

应用发起的文件写入由个人上下文模块内的受控适配器协调，SQLite 仍只有 storage worker 一个写者。文件读写、目录扫描和表征推理全部在数据库事务外；跨介质操作通过只含身份、预期摘要、目标摘要、阶段和幂等键的可恢复记录协调，不把正文塞进操作日志。

推荐协议如下，不能称为文件与 SQLite 的原子事务：

1. 校验目录身份、用户动作、当前修订及读入时文件摘要。建立准备记录，相关条目在不一致期间不得参与 Agent 输入。
2. 新建使用 Win32 独占创建；修改使用 shareMode=0 打开现有文件。原生模块持有根目录和父目录句柄，拒绝重解析与硬链接；句柄取得后核对身份和预期字节摘要。
3. 在受控恢复目录保存并刷盘旧/新暂存材料，同一独占句柄写入并 FlushFileBuffers，直到 SQLite 治理提交后才释放。不会用检查后 rename 替代排他保证。此协议已有真实 Win32 竞争进程验证，常用编辑器交互仍单列实机验收。
4. 重读实际文件，核对目标摘要；storage worker 在短事务内登记新修订、确认与来源，并撤销依赖旧修订的关联和概览。此后才发布变化通知。
5. 重启恢复时按实际文件摘要判断：目标摘要匹配则幂等收束登记；旧摘要匹配则撤销未提交操作；其它摘要保留用户文件并呈现冲突。不从数据库恢复另一份正文。

原生模块缺失或竞争失败时拒绝写入，保留应用内草稿，允许用户刷新后重试。后台模型只提出候选，不自动覆盖已确认文件。

忘记、删除和来源撤销先使 SQLite 治理及读取资格失效，再处理文件/索引；这样文件删除失败、旧索引残留、迟到表征与模型响应都不能恢复引用资格。物理清理是否成功单独呈现。来源删除时，有独立有效用户确认的条目沿既有规则判断；仅由被删来源支持的条目退出读取。用户文件不因后台来源清理而被静默删除。

## 6. 关键词与向量统一进入 resolve

对外保留个人上下文模块的 `ingest`、`resolve`、`manage` 三接口。文件访问、确认核验、范围限制、两路召回、融合及预算都属于模块内部职责；recipe 和 renderer 不直接读文件、SQLite 或向量。需要扩展请求时追加版本化 exact 合同，旧 `search_context@1` 的冻结别名等值语义不偷偷升级。

推荐一次解析按以下顺序执行：

1. 检查 Agent 开关、个人记忆休眠、recipe 的记忆参考政策、授权范围与来源有效性，形成允许检索的当前修订集合。确认冲突与被撤销条目不得先进入两路召回再靠模型甄别。
2. 词法侧组合结构化精确字段、已登记别名、FTS5/BM25 与有界中文短词补充；向量侧只查询同一允许集合的有效表征。少量明确偏好在既有预算内保留独立分区，不依赖语义相关性才能生效。
3. 以 RRF 作为融合基线，按条目身份去重；融合参数、召回上界和确定性排序记录在检索政策中。候选与明确内容保持原有分区和权重规则，相关性不能升级确认性质。
4. 对选中结果重读 Markdown，复核正文摘要、治理修订及来源；整条纳入有界个人上下文包，返回来源、输入身份、检索降级与省略标记。不得将整目录塞入模型输入。
5. 模型外发与产物提交前再次复核相关身份；发生撤销、修订、取消或失租时拒绝迟到提交。

RRF 可以融合来自不同评分机制的排名，避免直接相加 BM25 与向量相似度。本方案借鉴算法，不引入 Elasticsearch；本项目是否改善质量仍需评测。[RRF 官方说明](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

中文不能直接依靠 trigram：FTS5 的 trigram 全文查询不匹配不足三个 Unicode 字符的子串，因此两字查询要有补充路径。[FTS5 trigram 文档](https://www.sqlite.org/fts5.html#the_trigram_tokenizer)

当前[会话问答检索](../src/runtime/storage-worker/question-retrieval-store.js)已实现临时 FTS5、BM25 候选与短词补充，最终还有词项命中排序；可复用其经核验的分词思路与失败经验，不能据此宣称个人记忆已有 BM25/向量混合检索。[个人记忆 resolve](../src/runtime/storage-worker/personal-context-store.js)目前仍按规范化语义键与别名等值过滤。

检索相关性不参与本人归属证明。个人记忆会话关联继续通过已确认信息、规范化字段及已登记别名等值核验，并绑定个人记忆 revision 与会话版本/水位/digest。“主题相近”不能证明本人说过、决定过或承诺过。

日期范围、精确计数、全部事项和否定存在性沿结构化读取或完整来源扫描；不能把 top-k 作为全集证明。会话问答已有的总结、经历与独立原文召回政策不在本次设计中被个人记忆索引替代。

## 7. 索引重建与字幕独立性

每个索引项绑定稳定条目 ID、个人记忆修订、正文摘要、解析政策及索引代际；向量额外绑定配置 revision、请求和响应模型身份、维度和归一化政策。一条记忆一个向量，旧模型、旧维度或旧正文不能混查。追加迁移为 v29–v32，v1–v28 不变。

重建从有效 Markdown 和 SQLite 治理记录开始，后台生成新代际，在短事务中发布。重建期间仍可读取摘要匹配的旧项；新建或改动项明确显示尚未索引，词法或有界直接读取提供降级并声明覆盖。撤销优先于代际发布，旧表征回写必须核对当前摘要并拒绝失效结果。

删除索引只触及派生数据，保留正文、来源与 suppression。丢失治理记录则不同：文件仍可阅读，但重新接入必须待确认，缺失来源明确显示；不能承诺仅凭 Markdown 恢复已验证来源和完整撤销语义。

用户选择云端表征：默认关闭，独立 HTTPS 服务、模型 ID、凭据与外发披露，不占用四个推理用途。只发送当前有效已确认记忆正文及查询。后台每批至多16条/32KiB，单次30秒、至多3次尝试；查询3秒期限，失败显式降级关键词。文件 I/O、网络与向量评分在数据库队列之外，索引写入短批让行，取消与关闭拒绝迟到结果。

向量模型缺失、损坏、退出或重建时明确回落词法；词法索引失败时允许有界当前正文读取并声明限制。目录故障时个人记忆停止注入，字幕开始、停止、持久化、字幕历史与原始版导出继续沿独立链路。退出不等待无界扫描或索引重建。

个人记忆在任何情况下不进入识别 provider、不改变首次稳定转写，沿 [ADR 0002](adr/0002-separate-subtitle-and-agent-systems.md) 与 [ADR 0017](adr/0017-retire-confirmed-recognition-terms.md)。会话总结记忆参考偏好关闭时，在文件读取、表征查询、路由、工具和模型输入之前排除个人记忆及跨会话关联；普通总结操作仍零自动写入个人记忆。

## 8. 迁移、携带与退回原配置

先追加迁移与管理合同，保持全部既有 SQL/checksum、旧 recipe 绑定及导出编码不变。不能直接修改 `INITIAL_SCHEMA_SQL`，也不能让文件初始化成为字幕启动条件。

推荐迁移只处理用户选择的已确认条目，记忆候选与会话经历记录沿用原路径：冻结迁移清单，独占创建 Markdown，核对各正文摘要，然后切换这些条目的权威位置。每条只有一个明确的权威位置；未切换条目仍读旧 SQLite，已切换条目只读文件，不允许两边独立编辑。中断后按清单和摘要恢复，不增加确认或来源证据。

目标治理存储仅保存已切换正文的引用、摘要及确认/来源/撤销元数据；既有正文列与外键约束如何迁移需要单独 schema 设计，不能简单置空现有 NOT NULL 列。迁移备份只能作为受控恢复材料，不参与运行读取；切换后的旧正文清理和 backup 保留规则必须在迁移旅程中验证，删除与撤销不能从备份被自动恢复。

用户自选目录意味着文件可以被其它软件读取或备份，不自动授权应用上传、同步或跨目录扫描。应用提供版本化的治理记录携带格式，只包含必要身份、相对定位、摘要、来源引用和撤销信息，不带凭据或绝对路径。它是用户明确触发的数据携带动作，不是诊断报告；不能把包含正文的文件写入 `.artifacts/` 或 `docs/validation/`。

仅复制 Markdown 可以携带可读正文；完整迁移管理语义还需要治理记录。外来携带包的来源声明不能自证真实：先校验当前本地来源与摘要，缺失来源明确提示，恢复确认通过用户明确动作进行。退回旧配置应使用迁移前一致快照或明确逆向迁移，不能让旧版本应用重新读过期 SQLite 正文并继续写成第二分支。

## 9. 建议的实施顺序与收益门槛

| 切片 | 交付内容 | 进入下一片的证据 |
|---|---|---|
| P0 | 文件发现/替换保存、双写竞争、断点恢复、现有 schema 迁移的有限探针；冻结解析和确认政策 | 证明不会覆盖外部保存、不会因根目录失联批量忘记、不会读取不一致正文；直接替换无法保证则采用提案/另存路径 |
| P1 | 自选目录、已确认正文迁移、外部编辑与确认、来源/撤销、中文词法检索、可重建索引和管理信息携带 | J21/J22/J28、DB1/DB7/J10/J12 的真实用户旅程，并在正式 Electron 表面验证管理路径；用户可以脱离应用读取/编辑正文 |
| P2 | 同一 resolve 中的云端表征召回与 RRF、版本化索引与取消/降级 | 固定题集比较词法、向量和融合；受控 provider 证明实现，真实 provider 质量另验，默认关闭 |

P0 结束后才承诺具体实现工作量。文件权威与向量各自有验收出口，不让模型下载阻止用户使用文件管理。

检索评估建议至少准备 100 条经人工标注的问题，覆盖项目名/编号、中文两字词、同义改写、简称、多义词、偏好、错误项目、无答案以及日期/全部事项；加入已删、已忘记、旧修订、休眠、未确认文件与记忆候选负例。三种算法使用相同有效集合、返回上界、上下文预算和用户设备条件，并保留一个不参与调参的验证集。

比较 Recall@10、Precision@10、nDCG@10、无答案误召回率与按查询类型的差异；同时记录冷/热 P95 延迟、内存峰值、索引大小、单次更新及全量重建成本。外来范围或被撤销正文进入上下文必须为零，作为正确性门禁，不与召回指标折算。

建议预先冻结默认启用向量的量化门槛，例如同义改写组 Recall@10 相对词法至少提高 5 个百分点，精确名称组质量与无答案误召回不劣于基线，并落在预先约定的内存和延迟预算内；用验证集与置信区间检查收益稳定性。此处是供选择的评测门槛，不是实测结果。性能预算要在明确目标设备后制定，不能从公开榜单推断。

## 10. 需要先登记的语义与真实旅程

SEM-F26 和 [ADR 0006](adr/0006-local-structured-personal-memory.md) 的旧正文位置及等值限制已由 SEM-F41/F42 和 ADR0025 局部替代。以下要求与旅程已按 SEM-T06 在产品改动前登记；旧工具与旧 recipe 的冻结语义仍保留。

| 登记落点 | 需要增加的要求或场景 |
|---|---|
| CONTEXT、SEM-F26/F30；局部修订 ADR 0006 | 已确认个人记忆正文的文件权威与范围；文件/数据库各自事实；版本化 resolve；保留三接口、来源与自动处理边界 |
| SEM-F27/F32/F37；J21/J28 | 候选确认建文件→外部纠正→旧关联/当前及上版概览失效→确认新修订→重建；手动操作零模型调用，外部保存不形成被动交互信号 |
| SEM-F07/T08；DB1/DB7/J10 | 追加 migration、可中断可重跑迁移、单正文权威、旧 checksum 不变；确认/忘记/删除在文件与 SQLite 不一致及重启时仍收敛 |
| SEM-F26/F30/F37；J22/J24/J28 | 两路过滤/融合→重读当前文件→有界上下文→Agent 结果；索引删除重建、旧模型/旧修订拒绝、中文短词、无答案及错误项目 |
| SEM-F38；J29/J30 | 参考关闭/休眠时零个人记忆输入；普通总结操作零自动记忆写入；来源撤销与迟到响应不恢复旧内容 |
| SEM-F14/T04；J12/J24 | 根目录失联、权限错误、格式损坏、重复 ID、替换保存竞争、删除文件失败、SQLite 回执丢失、表征故障与取消；故障后字幕新会话、历史与原始版导出独立 |

旅程使用真实设置 renderer、preload/main exact IPC、个人上下文模块、临时文件目录、storage worker/SQLite、调度器与 Agent Loop。产品内部模块不能用替身；系统权限、声卡、网络及 provider 边界按 SEM-T02 处理。实际 Win11 编辑器保存、目录失联与资源竞争仍需实机证据，不能仅凭合成文件事件宣称实机验收完成。

有一项既有文档缺口需后续核正：`data-architecture.md` §4.3 仍含已由 ADR 0017 取消的识别关键词通路；部分 A1/A2 叙述也沿用旧任务形态。本提案依据当前 SEM-F27/F30 和 ADR 0013/0017，不借旧叙述恢复 ASR 个性化或旧任务安排。
