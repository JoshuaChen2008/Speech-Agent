## 1. 工具条融入背景，锁定后才分离

### 原因

这个行为**以前是有的，今天上午被删掉了**。

提交 `115c684「fix: 恢复六点握把并隔离工具条主题」` 把 `toolbar.css` 里的「嵌入态 / 脱离态」两套样式整段删了：

- 原来未锁定时：`background: transparent`、无描边、无阴影、`opacity: 0.45`，hover / 拖动 / 需要介入时才提亮到 1。
- 原来锁定时：才长出底色、描边、阴影、分隔线。
- 改后：`.toolbar` 永远画 `var(--surface-toolbar)` 深色表面，`opacity: 1`。

那次提交的真实目的是「工具条配色不要被主题和字幕背景色翻转」，但顺手把「画不画表面」一起改了。这两件事其实不冲突——**主题隔离管用什么颜色，嵌入态管画不画**。

### 方案

恢复两态，同时保住主题隔离：

- 未锁定：`.toolbar` 背景透明、无描边阴影、整体降透明度（建议 0.45，可调）。字幕卡就在正下方，视觉上自然成为卡片的一部分，颜色不用同步——它本来就是透过去的。
- hover / focus-within / 拖动中 / `data-attention="on"` 时提亮到不透明。`toolbar.ts:334` 已经在写 `wrap.dataset.attention` 了，只是现在没有 CSS 消费它，**不用改 TS**。
- 锁定：长出 `--surface-toolbar` 底色 + 描边 + 阴影 + 分隔线，同时关掉图标光晕（有底色后光晕会让图标发糊）。
- 表面色继续用 `--overlay-*` 那组固定 token，不跟主题、不跟 `barColor`——这条保持不变。
- 高对比模式：`forced-colors` 分支保持现状（一律实边，不融入）。

### 影响

- `src/toolbar/toolbar.css`（主要改动）
- `test/ui/fluent-experience-ui.test.js` 里断言 `.toolbar { background: var(--surface-toolbar); … opacity: 1 }`，要改成「锁定态才有表面」
- `docs/current-ui-ux-handoff.md §3.1` 那句「工具条始终使用主题独立的深色半透明覆盖表面」措辞要改

工具条真实轮廓上报的是 `#toolbar` 的几何矩形，跟背景画不画无关，所以字幕窗的 `.tb-hole` 和 J17 命中不受影响。

## 2. 拖拽流畅度

### 原因

在 `src/main/manual-window-interaction-controller.js`。当前实现是**主进程开一个 8ms 的 setTimeout 轮询**，每次问 OS「光标现在在哪」，算出新位置，`setBounds()` 推窗口。四个原因叠加：

**① 轮询而不是跟事件。** 渲染进程本来就有高分辨率的 `pointermove`（还能取合并事件），但拖动完全不用它，改成定时器问 `screen.getCursorScreenPoint()`。位置天然比光标晚一拍，采样率也和鼠标报告率对不上，产生走样。

**② `setTimeout(8ms)` 在 Windows 上不成立。** 系统默认定时器精度 15.6ms，而且和显示器刷新不同步。实际 tick 在 8~16ms 之间乱跳，窗口位移不匀速——肉眼看就是一顿一顿的。

**③ 未锁定时每帧移两个窗口。** `dragTick()` 里先 `captionWin.setBounds()`，紧接着 `dock()` 又 `toolbarWin.getBounds()` + `toolbarWin.setBounds()`。两个窗口分别调 SetWindowPos，不可能原子，所以拖的时候工具条会相对字幕卡「游」一下。加上取光标，每 8ms 有 5 次同步系统调用。

**④ 两个都是 transparent + alwaysOnTop 的分层窗口。** DWM 每次移动要重新合成整个窗口，没有普通窗口的移动优化，成本本来就高，再乘以 ③ 的两倍。

### 方案（按性价比排序，建议分两步）

**第一步（低风险，只改一个文件，先做完实测）：**

- 拖动开始时记下工具条相对字幕窗的固定偏移，拖动期间直接按偏移推工具条，**不再每帧走 `dock()` 重算 + 两次 `getBounds()`**。5 次系统调用降到 3 次。
- 拖动只改位置不改尺寸，用 `setPosition()` 代替 `setBounds()`，少走一次 resize 路径。
- tick 间隔从 8ms 改成对齐刷新的 ~16ms。更快不等于更顺——现在的 8ms 有一半在空转，反而放大了定时器抖动。

**第二步（如果第一步实测仍不满意）：**

- 改成事件驱动：渲染进程在 `pointermove` 里把屏幕坐标发给主进程，收到就移动。采样点直接来自真实鼠标事件，不再有定时器抖动。渲染进程已经用了 `setPointerCapture`，光标移出窗口也照样收得到事件。
- 保留一个低频看门狗 tick（比如 200ms）兜底，防止渲染进程卡住时窗口跟不上或停不下来。

### 影响

- `src/main/manual-window-interaction-controller.js`（第一步只改这里）
- 第二步会碰 `src/ui/shared/manual-window-drag.js`、两个 preload、IPC channel
- `test/ui/window-drag-ui.test.js` + J17 联合旅程要跑

**这一项必须实机验收**，自动化测不出「顺不顺」。

## 3. 字幕文字颜色

### 原因

`tokens.css` 的浅色主题分支把 `--text-caption` 从白色改成了深色墨字（同时 `--text-caption-partial` 也跟着变）。设计意图是「卡片背景跟随主题，文字跟着背景走」，但和你的实际用法冲突——字幕卡是半透明浮在任意画面上的，底下是什么颜色跟应用主题没关系。

### 方案

分两半：**先修默认，再加自定义。**

**默认恒为白：** 把 `--text-caption` / `--text-caption-partial` 从浅色主题分支里拿掉，让它们在两个主题下都是白色。同时保留深色文字阴影（`--text-shadow-caption`），这样白字压在浅色画面上也读得出——这也是 VLC / OBS / Aegisub 这类字幕工具的通行做法：**文字色独立于皮肤主题，可读性靠描边保证，不靠背景**。

**加自定义：** 新增配置字段 `captionTextColor`，走和现有 `barColor` **完全一样**的路径（这条路已经铺好了，照抄即可）：

| 环节 | 文件 | 做什么 |
|---|---|---|
| 默认值 + 校验 | `src/main/services/config-store.js` | `null` 或 `#rrggbb` |
| 渲染进程写入白名单 | `src/main/ipc/access-policy.js` | 加进 `RENDERER_CONFIG_KEYS` |
| 配置 → CSS 变量 | `src/ui/shared/appearance.js` | 有值就 `setProperty`，留空就 `removeProperty` |
| 设置页控件 | `src/settings/settings-view.tsx` | 「显示与字幕」加一行取色器 + 「还原默认」链接 |

**兜底：** 颜色非法或留空 → `removeProperty` → 回到 token 默认白色。`appearance.js` 处理 `barColor` 已经是这个写法，同一套逻辑。

**临时字幕不用单独设一项**：从用户选的颜色按 60% 弱化推导出来，保持现在的层次关系。

**高对比模式**下系统强制色会自动接管，用户色失效——这是对的，不特判。

后续如果还想要「描边颜色 / 描边粗细」（OBS 那种），再单独加一轮，本轮不做。

## 4. 光标在工具条上跳跃

### 原因

在 `src/toolbar/toolbar.ts` 的 `applyHit()` 加主进程的 `setIgnoreMouseEvents`。

工具条窗口是 600×72，但真实的条只占右边一小块，其余全透明。所以渲染进程每次 `mousemove` 都做一次命中判定：压在 `.toolbar` 上就让窗口变实心，否则变穿透。**穿透时光标形状由下面那个应用决定**（比如浏览器里就是 I 形文本光标），实心时才是工具条的箭头。所以每翻转一次穿透状态，光标就换一次外形——这就是你看到的「跳跃」。

会反复翻转，是三个原因叠加：

**① 判定滞后一帧多。** `mousemove` → rAF 合并（1 帧）→ 异步 IPC 送到主进程 → 才真正切换。这条链至少 16ms 起。光标在条的边缘附近移动时，穿透状态永远是「上一帧的答案」。

**② 零迟滞。** 判定是精确边界比较，光标压在边上抖动 1px 就翻一次。配上 ① 的滞后，就来回横跳。

**③ 有一条 1px 的死带。** 工具条上报的真实轮廓，在 `window-layout-contract.js` 里经过 floor/ceil 取整后变成字幕窗的 `.tb-hole`，所以洞比条最多大 1px。这一圈里工具条说「不是我的」，字幕窗说「是洞，也不是我的」，两个窗口同时穿透，光标掉到底层应用上。

### 方案

- **加迟滞带：** 进入用真实轮廓判定，离开要超出轮廓 6px 才恢复穿透。6px 大于 ③ 的 1px 误差，那条死带自然被盖住。
- **去掉 rAF 延迟：** 把 `elementFromPoint` 换成缓存矩形的坐标比较（rect 已经有 ResizeObserver 在维护了）。判定成本降到几乎为零，就可以在 `mousemove` 里同步算，只在结果真的变化时才发 IPC。少一帧延迟，也顺带省掉一次强制布局。
- **统一光标声明：** 给条和子元素显式声明光标（条 `default`、按钮 `pointer`、握把 `grab`），减小翻转瞬间的视觉落差。
- `.tb-hole` 比条大 1px 是故意的 fail-safe（宁可洞大也不能点不到），**不动**。

### 影响

`src/toolbar/toolbar.ts`、`src/toolbar/toolbar.css`。不碰主进程、不碰窗口几何、不碰 J17 契约。

## 5. Ctrl+Alt+L 锁定/解锁

### 现状（重要）

**功能其实已经能用了。** `src/main.js:879` 已经注册了 `CommandOrControl+Alt+L`，退出时 `unregisterAll`。缺的是三件事：

1. **前端完全不知道它存在**——工具条锁定按钮的提示里没提，设置页里也没有。用户不看代码就不知道有这个键。
2. **硬编码，不能改。**
3. **注册失败没有任何回执。** 被别的软件占用时 `globalShortcut.register` 会返回 false，现在这个返回值被直接丢掉了，用户只会觉得「按了没反应」。

### 方案

**新增配置字段 `lockShortcut`**（默认 `CommandOrControl+Alt+L`，允许关闭）。

注意：它**不能**走 `barColor` 那条「渲染进程直接写配置」的白名单路径。因为注册可能失败，必须是「提交意图 → 主进程试注册 → 返回回执」，跟模型下载同一类。所以新开一对 IPC，只允许设置窗调用。

**主进程：** 抽一个注册函数，先注销旧的再注册新的；成功返回新值，失败回滚到旧值并返回明确错误（冲突 / 非法组合），把权威值广播回设置页。**不做乐观更新。**

**设置页：** 新开一个「快捷键」分组（或放在「显示与字幕」下面），一个录制框：聚焦后按组合键 → 拼成快捷键字符串 → 提交 → 显示回执。需要拦截：只按修饰键不算、必须至少带一个修饰键、Esc 取消。旁边给「恢复默认」。

**工具条：** 锁定按钮的提示文字追加当前快捷键，变成「锁定字幕（Ctrl+Alt+L）」。工具条只读不写，把 `lockShortcut` 加进广播的配置即可。

**字幕窗：** 底部那行「已钉住」提示也带上快捷键。**这条其实是最重要的**——锁定后整个字幕窗穿透，万一是误锁，快捷键是唯一出口，得让用户在那个界面就看得到。

### 影响

`src/main.js`、`src/main/services/config-store.js`、`src/main/ipc/channels.js` + `access-policy.js`、`src/preload/settings.js` + `toolbar.js`、`src/settings/settings-view.tsx`、`src/toolbar/toolbar.ts`、`src/caption/caption.ts`。

需要一条新旅程：改快捷键成功 / 冲突失败回滚 / 关闭后按键无效。

## 6. 本地 vs 云端的状态区分（方案，等你确认后再实现）

### 先说清楚现状

`RuntimeSnapshot` 里**没有任何「这段字幕是谁产出的」这个事实**。它只有运行阶段（8 个）、音频源、本地模型状态、最近错误。而 `runtime-view.js` 的颜色轴只有 5 档（中性 / 忙碌 / 活跃 / 警告 / 危险），已经被 8 个阶段占满了。

**所以这不是能靠改 CSS 做出来的，必须先加契约字段。** 这一节是 contract request，不是实现计划。

### 核心设计：处理位置是独立的一根轴

新增一个和运行阶段**正交**的字段：

```
processing = {
  locus:    'local' | 'cloud'     // 这一刻实际在用哪一路，不是用户配置了什么
  degraded: true | false          // 是不是降级的结果
  reason:   字符串 | null          // 降级原因，来自后端，UI 不编
}
```

**为什么 `degraded` 要单独一个字段，不能只看 `locus`：** 用户本来就选本地时，「本地」不是降级，不该报警；只有「想用云端但正在用本地」才是你要感知的事件。两个字段分开，UI 才不用去猜用户的意图。

### 视觉编码

在工具条状态区的运行图标**左边**加一个常驻小徽标，它是运行阶段之外的第二个恒定元素：

| 状态 | 形状 | 文案 | 颜色 |
|---|---|---|---|
| 本地（正常） | 芯片图标 | 本地 | 中性，不抢眼 |
| 云端（正常） | 云图标 | 云端 | 蓝（复用「忙碌」那档） |
| 云端 → 本地（降级） | 云 + 斜杠 | 本地（已降级） | 琥珀 + 淡底色 |
| 云端连不上、重试中 | 云 + 旋转 | 连接中 | 蓝 |

五条设计决定：

1. **正常态用中性色，只有降级才上色。** 这样「发生降级」是一次真正的视觉变化，扫一眼就看得到。如果两个正常态都花花绿绿，降级反而被淹没。
2. **形状是主编码，颜色是冗余通道。** 芯片 / 云 / 云带斜杠——三个形状本身就能区分，色盲和高对比模式下依然成立。这是 `phases.css` 开头就立下的规矩，不破。
3. **降级触发「需要介入」态**，工具条恒亮不再淡出——正好和问题 1 的嵌入态联动，降级时条会自己浮出来。
4. **不弹窗、不抢焦点、不发声。** 和精修故障通知同一条规矩。
5. **不用扩颜色轴。** 中性 / 蓝 / 琥珀三档现成的够用，`phases.css` 的色值一个都不用改。

**字幕窗那边不加任何标记。** 现有规则已经明确「运行中不新增提示、徽标或颜色状态」，处理位置属于运行事实，归工具条管。

### 现在就该定、否则以后返工的两件事

- **条会变宽。** 工具条是右对齐自适应的，加一个徽标会让真实轮廓变宽，字幕窗的洞跟着变——这条链已经是自动的，不用改代码，但 J17 旅程要补一个「带云端徽标」的轮廓用例。
- **字幕历史也该能追溯。** 导出的文稿里应该看得出某一段是本地还是云端产出的，否则出了问题无从对账。这是存储结构的事，比 UI 大，建议单独一轮。**本方案标出这个依赖，本轮不做。**
