# 会话问答与会话经历记录优化规划

> 2026-10-01 已决定并授权全部实施；2026-10-02 状态为实现完成·尚未验收。实施登记与逐项进度见[change](../openspec/changes/implement-summary-first-session-question/tasks.md)，当前证据与限制见[交付记录](validation/session-question-summary-first-2026-10-02.md)。术语依据 [CONTEXT](../CONTEXT.md)，个人记忆沿用[提问优先规划](personal-memory-question-first-plan.md)及已登记语义。

推荐主链路：**终态会话分段整理 → 保存带来源的会话经历记录 → 问题检索相关要点 → 有界读取对应原文 → 回答并跳转来源。** 复用已有会后结构化纪要；随着细分经历记录积累，避免每次问题重新对整场正文逐块调用模型。

| 内容 | 职责 | 问答使用方式 |
|---|---|---|
| 权威原始转写 | SQLite 内的事实来源；不被派生产物覆盖 | 独立参与检索，按稳定字幕事件引用核对细节 |
| 会话经历记录，UI 称“会话要点” | 可检索的细分经历；每项有时间范围、来源和输入身份 | 默认检索入口，保留决定、否定、变更、待办等依据 |
| 会后结构化纪要，UI 称“会话总结” | 给用户阅读的整场概览 | 复用有引用条目帮助定位；不承担全部细节索引 |
| 个人记忆 | 本人陈述、长期要求及明确确认内容 | 按相关性、范围和预算读取；偏好作为产出约束，事实作为来源 |

会话经历记录从权威来源直接整理。普通纪要及其接受、编辑不会反向写入个人记忆；会话里的“我”、mic 或 loopback 不证明本人身份。保留字幕原文不意味着永久保留正式 Agent 原始提示；后者继续遵守信号提取后的清理边界。

实施前的路径有三项关键缺口（保留为改动依据）：

- [摄取 runner](../src/agent/execution-host/context-ingest-session-runner.js) 仍将整场会话序列化到单次请求，限制为 15,000 UTF-8 字节。直接改成依赖经历记录，会把长输入失败提前到摄取阶段。
- [经历存储](../src/runtime/storage-worker/personal-context-store.js) 的会话概览取 `output.experiences` 前 8 条文本，概览条目没有分别保存该输出中的 evidence。需要可分页、逐项带来源的细分记录，不能仅扩大整场概览。
- [正式问答 runner](../src/agent/execution-host/formal-agent-run-runner.js) 的 `qa.answer@3` 仍规划全部冻结正文；已有 `search_context@1` 只做个人记忆别名等值匹配，不是全文检索。上述代码事实不证明用户这次失败的具体预算轴；实施首片应查看一次失败运行的无正文诊断。

已按以下顺序实施，既有结果仍按原版本解释：

1. **先固定来源、产物与运行合同。** 每项经历绑定会话、正文版本、提交水位、digest、稳定字幕事件范围和产物版本。可读时间由来源事实解析，区分会话日期、相对位置和生成时间。沿现有历史导航定位正确版本及分页内原文，查看来源零模型调用。新字段通过版本化合同或外层结构登记，不往 exact `SourceRefV1` 暗加字段。
2. **让会话经历摄取支持长输入和增量积累。** 终态会话冻结完整提交边界，按实际请求容量分段，逐段生成独立、可校验的最终经历记录。每个登记的范围工作成功后，同一 SQLite 事务提交产物和处理进度；失败、取消或失租不推进。已提交范围可复用，缺口显式保留；整场纪要及问答仍只提交完整最终结果。这个设计需要先登记为范围级产物与工作，不能把现有 Loop 临时输出改名持久化。处理进度、源提交水位和索引覆盖分别记录，不能相互替代。后台只处理现有开关、资格和新自动边界允许的来源，旧历史由用户选定后整理。
3. **接入单会话检索问答。** 在授权范围内合并经历、已有纪要及原文检索候选，去重后读取少量相邻正文。原文召回独立进行，避免总结漏掉的细节失去入口。先验证 SQLite 中文短词、数字、日期和标识符检索；全文索引属于可重建投影，需要新语义登记，不能偷换现有个人记忆等值匹配。宿主对系统提示、问题、候选、正文、工具增长和输出空间整体预检，超预算显式收束，实际 token 用量只取 provider 回执。无总结时走有界原文检索，不强制先生成整场纪要。
4. **扩展跨会话问题。** 具体事项的变化按时间联合检索并核对修订；日期或项目总览冻结会话目录，分页读取全部有效要点、分批分析再合并。显示纳入范围及未整理、失效、排除部分。精确次数、全部清单和“从未提到”需要结构化计算或完整来源扫描，不能由 top-k 推断。语义索引和重排在基线召回不足时再评估。

个人记忆继续使用已有候选、确认、冲突 revision 和撤销规则，无需为本轮问答重建五层文件。借鉴 PENDING 的批次思想时，冻结候选 ID 与 revision，模型只提出整理方案；模块复核来源后以 SQLite 事务提交，只消费该批次，期间新候选留到下一批。明确内容不被自动覆盖，也不通过纪要二次提炼提高确认状态。NOW 的短期事项可由有效待办及经历形成有时效投影；SELF 的陪伴型自我模型不纳入本轮方案。个人记忆不会整份常驻注入。

akashic-agent 的历史实现支持这种职责分工及增量整理思路：[初期存储代码](https://github.com/kachofugetsu09/akashic-agent/blob/a92dae07e2dca729d7e37ff0c113299e565e5496/agent/memory.py)、[后续记忆整理器](https://github.com/kachofugetsu09/akashic-agent/blob/96fcbe8c7e1a134b75183bc9755fdc34a9468b0e/proactive/memory_optimizer.py)。后者的候选快照隔离新追加，但写 MEMORY、追加 HISTORY 和删除快照是不同文件操作，不能作为整体原子事务的证据。本项目借鉴分工，采用现有单写者、租约和 SQLite 事务治理。

单会话及跨会话切片均已实施：**长会话形成有界经历记录；重复提问复用整理结果；细节遗漏仍能从原文查找；每个重要结论能跳转依据。** 会话级处理覆盖不等于摘要语义无遗漏。首版跨会话冻结原文总上界仍为4 MiB/50,000段，超界明确拒绝；语义索引、重排及更大范围的流式冻结另行评估。

采纳后先登记 SEM-F26/F28/F30/F31/F34/F38/F39/F40、相关 ADR 0009/0021/0023、J21/J22/J24/J29/J30/J31 与 DB1/DB7/J10/J12，再实施版本化 recipe、分页接口及追加 migration。原绑定、checksum、旧结果和导出编码保持兼容；原提示及 Loop 中间文本的零持久化边界继续成立。

验证用合成来源对照“现有全文分块 / 仅总结检索 / 总结与原文共同检索”，检查遗漏细节、否定、较晚修订、中文短词、跨会话联合证据、引用定位、覆盖缺口和预算边界。仅总结对照是来源可供性的消融检查，不把它伪装成真实模型问答评分。内部模块使用真实实现；内容质量另以真实 provider 评估。证据 JSON 只写指标、枚举、相对耗时和哈希，不含正文、路径或现场音频。当前实现接入正式入口，确定性检查和真实 provider/实机边界见交付记录，状态不晋级为实机或发布验收。
