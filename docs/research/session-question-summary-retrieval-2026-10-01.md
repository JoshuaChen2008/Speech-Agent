# 会话问答：总结检索、来源定位与跨会话分析研究建议

结合 akashic-agent 历史实现后的精简总体方案见[会话问答与会话经历记录优化规划](../session-question-summary-first-plan.md)。该规划补充了会话经历摄取的 15,000 字节限制及逐项来源缺口，并将分段整理置于检索问答之前；本文保留外部方法比较和代码核查依据。

## 1. 总体建议

建议把重复问答的默认输入准备改为：**先用会话总结定位主题，同时允许权威原始转写参与召回，再按字幕事件读取少量相关正文；跨会话总览另走范围覆盖明确的分批分析。**

```text
已保存的会后结构化纪要 ──检索──┐
                              ├─合并候选→校验来源→读取有界正文→回答与可点击来源
权威原始转写的可重建索引 ─检索─┘

明确日期/项目范围→冻结会话目录→分页读取全部有效总结→分批分析→引用正文核对
```

这个方向保留用户提出的“总结内容 + 时间戳 + 事件定位”，并补充两点：

1. **总结是查找入口，也是内容派生产物。** 它不能成为唯一的细节入口；否则首次总结漏掉的日期、数量、例外、否定或后文修订，后续问答可能永久找不到。
2. **局部问题与全局问题使用不同的输入准备。** 检索相关片段适合局部事实问题；“所有会话的主要变化”需要遍历范围内的总结目录；“列出全部事项”“总共有多少次”“是否从未提到”需要更强的完整证据策略。

总结构建仍需要至少一次对冻结输入的有界处理。已有长输入分块方案可以承担这个准备成本；后续问题不应默认重新对整场权威原始转写逐块调用模型。减少重复处理的收益须用本项目的实际请求数、输入字节、provider 用量及相对耗时验证。

## 2. 一手资料比较

| 方法 | 核验到的机制或限制 | 对本项目的研究建议 |
|---|---|---|
| 只检索总结 | Anthropic 在其 Contextual Retrieval 实验中报告，summary-based indexing 表现较低；这只适用于该实验，不能推出所有摘要方法都无效。[官方说明](https://www.anthropic.com/engineering/contextual-retrieval) | 总结适合作目录和主题入口；保留独立的原文检索，避免总结遗漏阻断来源查找。 |
| Contextual Retrieval | 给每个原文块附加针对该块的上下文，再建立词法和语义检索；官方区分这种上下文与通用文档总结。[官方说明](https://www.anthropic.com/engineering/contextual-retrieval) | 首片先附会话身份、日期、正文版本及来源范围等确定性信息。模型生成的局部说明后置评估；这种简化不等同于复现完整论文实验。 |
| parent-child / small-to-big | LangChainJS 官方实现先检索小块、按父身份去重，再读取较大父块，并分别限制子块和父块数量。[官方源码](https://github.com/langchain-ai/langchainjs/blob/main/libs/langchain-classic/src/retrievers/parent_document.ts) | 小范围用于召回，正文读取扩展到相邻字幕段或有界时间窗口；父范围也必须有字节上限，不能回到整场会话输入。只借鉴方法，不引入框架。 |
| RAPTOR | 作者提出对文本递归嵌入、聚类、总结，从多个抽象层检索；底层原文和较高层总结共同参与。[原论文](https://arxiv.org/abs/2401.18059)、[作者官方实现](https://github.com/parthsarthi03/raptor) | 借鉴分层表示。首片使用会话及来源连续范围即可，暂不引入向量聚类、递归主题树和维护整个树的生命周期。 |
| GraphRAG local / global | local 将特定实体的结构化关系与原文结合；global 对某层社区总结分批 map-reduce，用于跨数据集聚合问题。[local 官方文档](https://microsoft.github.io/graphrag/query/local_search/)、[global 官方文档](https://microsoft.github.io/graphrag/query/global_search/) | 借鉴局部和全局问题分路，先用已有会话/日期/项目范围，无需先构建知识图谱。 |
| DRIFT / LazyGraphRAG | DRIFT 用社区信息形成起点，再做局部后续问题；LazyGraphRAG 延迟模型处理，并以相关性测试预算限制探索。[DRIFT 官方文档](https://microsoft.github.io/graphrag/query/drift_search/)、[LazyGraphRAG 官方说明](https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/) | 借鉴按问题获取证据、固定探索预算和明确停止条件；首片不迁入图算法或开放探索循环。LazyGraphRAG 官方页面说明其已集成特定 Microsoft 产品，不能据此承诺可直接嵌入当前 Electron 应用。 |
| 长上下文直接输入 | Lost in the Middle 在当时受测模型和任务中发现，证据位于较长上下文中间时表现可能下降。[原论文](https://arxiv.org/abs/2307.03172) | 短范围直接输入可保留；加大窗口不是对所有问题的质量保证。该论文不证明当前配置模型存在相同幅度的问题。 |
| 时间与跨会话评估 | LongMemEval 分别考查信息提取、跨会话推理、时间推理、知识更新和拒答；论文指出更细的会话分解与时间关联有帮助，进一步压缩成孤立事实可能损失信息。[原论文](https://arxiv.org/html/2410.10813v2) | 把日期、否定、后文修订、多个来源联合推理和证据不足的拒答分别作为评估类别；不能只检查答案 Schema。 |

以上资料支持的共同取舍是“压缩表示帮助查找，原文承担核对，范围与预算由宿主治理”。它们没有证明总结 top-k 能覆盖所有相关事实，也没有证明全量处理后的总结语义无遗漏。

## 3. 适合本地 Electron + SQLite 的最小方案

### 3.1 两类召回共同形成候选

- **总结内容**：复用已保存纪要的概要、结论、待办、风险及已有来源引用。检索结果保留结果身份与版本，不能把旧结果和新输入混用。
- **权威原始转写**：建立绑定正文版本、水位和 digest 的可重建文本索引。即使总结未提到某个细节，仍允许原文结果进入候选。
- **范围过滤**：先由宿主落实授权会话、日期范围或项目；模型生成关键词不能扩大范围。
- **来源读取**：候选只携带受控引用和有界短内容；读取相关正文时按事件范围核验、去重，并在预算内扩展相邻上下文。

不要先选少数会话总结，再只搜索这些会话中的原文。这个硬过滤会让第一阶段没有召回的会话永久退出证据集合。可将总结和原文检索结果合并，再按范围、相关性和来源多样性选择。

首片可以用 SQLite 的结构化筛选与文本检索，不建立独立远端数据源。语义索引属于 CONTEXT 已定义的后期可选能力；若基线对同义表达的召回仍不足，再评估它及重排。索引删除或重建不能影响字幕历史。

### 3.2 中文文本检索不能只说“加 FTS5”

SQLite 官方文档说明，默认 `unicode61` 按连续 token 字符组成词；由此推导，无空格中文不会自动获得中文词切分。`trigram` 支持子串，但不足三个 Unicode 字符的全文查询不匹配；不能把大量两字中文词直接交给它。[FTS5 官方文档 §4.3](https://sqlite.org/fts5.html#tokenizers)

建议先验证仓库实际 SQLite 构建支持的功能，以三字以上子串索引和英文词法检索形成基线；两字词、精确数字、日期、代码或标识符另有范围受限的精确匹配路径。大范围扫描必须分页、可取消且有时限。是否需要中文分词器，以合成问题集的召回和延迟证据决定，不能预先声称任一 tokenizer 已解决中文检索。

### 3.3 最终纪要也有容量和信息损失

最终纪要是受输出 Schema 和容量约束的产物，不能假定一场数小时会话的全部细节都能进入它。检索准备可先复用最终纪要；若需要更细的总结，应另行登记**有明确来源范围、身份、版本和删除规则的持久派生产物**。

这与保留 Agent Loop 的临时分块归并输出不同。ADR 0009/0021/0023 规定分块正文和模型中间输出不持久化，不能直接把临时输出写 SQLite 来实现缓存。未来若采纳细分总结，需明确它是产品产物，只有受控生成成功后提交，具有源版本失效和撤销治理。

层级总结始终由明确的有效来源重建。不得无限地只对上版总结再次总结，逐渐丢失否定、细节和来源；旧综合正文不能成为新的权威事实。

## 4. 按问题准备输入，并明确回答覆盖

| 用户问题性质 | 建议的输入准备 | 可以主张的覆盖 |
|---|---|---|
| 某个决定、日期、参数、原因或具体片段 | 总结与原文共同召回，读取有界正文，并核对相邻否定与修订 | 回答建立在列出的证据范围上；未命中不等于从未发生。 |
| 多个会话中同一事项如何变化 | 先按明确事项与时间范围召回，跨会话保留时间顺序，核对较晚修订 | 说明纳入的会话与证据缺口，不把局部检索说成全量分析。 |
| 明确日期范围/项目内的主题、风险与趋势 | 冻结会话目录，分页遍历范围内全部有效总结，分批形成针对问题的中间结果，再核对关键正文 | 能说明总结目录覆盖及未生成、失效或受限会话；不能因此保证原文所有细节无遗漏。 |
| 全部事项、精确次数、是否从未提到、无遗漏审计 | 可确定性计数的结构化事实直接计算；正文语义问题需要针对问题完整扫描冻结范围，分批提取和核验 | 全范围处理、缺口和预算必须可检查；摘要不支持对原文“未提到”的完整性断言。预算不足时缩小范围或明确拒绝这种保证。 |

**三个维度必须分开：**

1. **总结覆盖**：范围内共有多少会话，其中多少具有当前有效的总结，哪些缺失或失效。
2. **原文证据覆盖**：实际读取的字幕事件及 code point 范围，是否遍历冻结输入全部范围。
3. **语义无遗漏**：模型是否保留并正确理解全部相关事实。前两者不能证明这一点，只能通过内容评估降低风险。

即使总结覆盖为整场、所有会话的总结都被读取，答案仍不能自动声称“所有原文事项均已纳入”。top-k 是相关性选择规则，目录遍历是范围覆盖规则；两者需要分别记录。

## 5. 时间戳、字幕事件与历史跳转

建议以段落或结论为单位关联来源，避免只有一份纪要的末尾统一引用整个会话。每条来源至少保留或可确定性解析：

| 信息 | 用途 |
|---|---|
| `sessionId`、正文版本、输入水位、input digest | 绑定冻结事实，避免跨会话或版本串用。 |
| `fromEventOrder` / `throughEventOrder` | 稳定定位首次稳定转写的来源范围，不按标题或时间模糊猜测。 |
| 必要的 Unicode code point 子范围 | 超长单段的精确来源与高亮；读取和显示仍须有界。 |
| 来源发生日期及会话内相对起止范围 | 给用户呈现可读的时间位置；由字幕事实计算，不让模型凭空填写。 |
| 总结/产物身份及版本 | 指明被检索的是哪版派生内容，区别源日期、生成日期和更新时间。 |

“事件”需区分：`caption_events` 中的字幕事件是权威原始转写事实；总结中的决定、待办、风险是派生内容，不能被伪装成新增字幕事件，也不证明某个说话人身份。

每个重要答案断言可以显示“会话日期 · 相对时间范围”，点击后走经主进程校验的受控目标，打开字幕历史并定位、高亮原文。查看来源应是零模型调用、零交互记忆信号的只读动作。来源被删除、撤销或版本不符时明确失效；不显示缓存旧摘录。内容推论与原文陈述应有清楚区别。

时间过滤不能只看总结生成时间。问题中的“上周”“后来”“目前决定”应结合用户所选范围、来源发生时间和实际后文修订；无法确定的日期或冲突应明确，不能以时间戳较新自动认定任意文本更权威。

## 6. 预算、生命周期与后续登记边界

有了检索，仍可能因为候选、父范围、工具结果和后续消息增长而超预算。建议由 Agent 执行宿主在外发前计算并强制：候选数、单页/单来源正文、累计工具结果、实际序列化请求、模型输入、输出额度、工具调用数及运行时限。模型能力配置中的 `maxInputTokens` 与 `maxOutputTokens` 分开解释，遵循项目既有请求容量策略；provider 用量未知时仍保持未知。

候选去重后按范围和来源多样性分配有界正文，不能只增加 top-k。预算内证据不足时，回答列出限制并允许明确扩大范围；不得静默截断后声称完整。取消、迟到提交拒绝、冻结模型运行绑定、重启后的显式继续或重新输入、字幕独立性继续受 J24/J30/J12 约束。

如果采纳方向，实施前需登记这些规划变更：

- SEM-F28、ADR 0009/0023：问答从每次完整输入处理转向明确的检索范围政策；有总结优先利用，没有总结仍有受控路径。现有禁止问答依赖预生成纪要的条款可以版本化修订，不能用旧条款否决用户提出的新方向，也不能在实现里悄悄改义。
- SEM-F38/F39、ADR 0021：纪要来源粒度和可能新增的持久派生产物；临时分块输出仍遵循当前零持久化要求，除非另行明确修订。
- SEM-F31/F34：问答引用、来源跳转、受控工具 Schema 和范围/覆盖投影；新的正文检索或来源工具不能从既有静态授权中推定。
- SEM-F07/T08：若新增 SQLite 投影、索引或派生产物，追加 migration，保留旧 checksum、结果和导出编码；删除、撤销和索引重建同样进入旅程。
- SEM-F14/F40：诊断与研究验证仅记录计数、枚举、相对耗时和哈希；正文可以按正式产品合同出现在受控产物与工具调用记录中，不能复制到日志或证据 JSON。

## 7. 验证建议

先建立不含现场内容的合成问题集，对照现有完整输入策略、只检索最终纪要、总结与原文共同召回三种方法。分别测召回、答案依据、引用定位、预算与等待；不以单一平均分替代失败类别。

最低类别包括：总结故意遗漏的细节、两字中文词、日期/数字/标识符、否定、较晚修订、跨块与跨会话联合证据、没有证据、范围内缺失总结、源版本变化、撤销/删除、预算临界与取消。global 类问题额外核对会话目录覆盖；枚举/计数不得只用检索局部样本验证。

实施旅程应复用或扩展 J22/J24/J29/J30/J31/J12；内部 renderer/preload/main、个人上下文模块、宿主、storage worker/SQLite、HistoryService 使用真实实现，仅替代 provider/网络/声卡/系统权限等外部边界。内容质量需真实 provider 另评；时间和跳转交互需正式 Electron 路径与适用实机证据。纯研究文档不启动产品回归，也不晋级验收状态。

实现职责建议保持现有边界：个人上下文模块拥有范围解析与来源投影；storage worker 拥有版本化派生产物、索引与源事实读取；Agent 执行宿主拥有检索输入准备、预算及取消；main/preload 拥有受控来源导航。renderer 不直接查询数据库，模型不拥有 SQL 或文件访问。

还有三个需要在规格中显式裁定的地方：

1. **检索的派生内容与权威输入分开。** 复用当前纪要时记录其模型身份、输入版本、水位、digest、记忆参考政策与结果版本。来自个人记忆或其它会话的推论，不能借一条当前会话总结进入未经授权的查询范围。会话经历记录可以作为并列候选，但不与会后结构化纪要或个人记忆合并成同一事实类型。
2. **持久索引与临时正文分开。** 词法索引是可重建投影，原文读取仍从首次稳定转写的事件锚点取得；优先保存范围身份与索引所需派生数据，不新增可恢复的分块正文库。更细的持久摘要只有在登记为独立派生产物后才能引入；完整目录与每项有效性必须可核验。
3. **旧合同与新政策分开。** `SourceRefV1` 是 exact 四字段，不能原地塞入时间戳、水位或 code point 字段。可在新外层元数据中关联，或增加新的合同版本。模型运行绑定、静态工具授权、既有 migration/checksum 与导出编码保留原解释；新 recipe/policy 版本在实施时按当时目录顺延。

## 10. 四阶段实施建议与可检查出口

以下是建议顺序，尚未采纳，不表示任何新能力已决定或已验收。每阶段实施前先登记对应 SEM 与既有 J 旅程；本轮不创建新的旅程 ID 或测试 lane。

| 阶段 | 最小实施范围 | 可检查出口与验证归属 |
|---|---|---|
| 1. 来源与输入政策 | 核对一次失败运行的预算轴；登记总结优先问答政策及新版本；复用有引用纪要条目，补时间范围显示、历史精确跳转与返回结果；裁定更细持久摘要的生命周期 | J22/J29/J30 + J10：从结果点击来源，跨分页定位正确会话/版本/事件范围；查看零模型调用。旧纪要缺引用、来源删除、导航失败/迟到、原始版/精修稿隔离有明确结果。 |
| 2. 单会话有界问答 | 总结与原文共同检索；中文短词及数字/日期精确路径；去重后按事件读相邻有界范围；由宿主拼接请求并校验实际容量；没有纪要仍有受控原文路径 | J22/J24/J30/J31 + DB1：总结故意未保留的细节仍可从原文找到；后文修订与否定有证据。重复提问不重新对整场正文逐块调用模型；小窗口、工具结果增长、证据不足、预算耗尽、取消/迟到与重启均受既有治理。 |
| 3. 跨会话与全局分析 | 用户明确选择日期/项目范围；冻结会话目录，保留来源时间顺序；局部比对共同召回，全局主题分页读取范围内全部有效总结；枚举/计数使用单独完整证据准备 | J22/J24/J30/J31：验证多个会话共同支持一个回答、较晚明确修订、同名不同项目隔离。显示总结缺失/失效与实际覆盖；全局请求不能只读 top-k 就宣称范围完整。可确定性计数的事实由宿主计算，模型推理仍不承诺语义无遗漏。 |
| 4. 按质量证据增强 | 用合成问题集与真实 provider 对比词法基线；同义表达召回不足时再登记可重建语义索引与重排；跨会话实体关系确有价值时再评估图方案 | J24/J31 + J12 与适用实机证据：模型输入、实际请求数、相对等待、引用依据和召回质量均有对照。索引失效、缺扩展、重建、删除与授权变化有显式降级，字幕仍独立。 |

阶段 1 与阶段 2 构成首个产品切片；不以向量扩展、知识图谱或所有旧历史预处理为前置。已有总结先复用，旧历史按用户当前请求范围按需准备，不在打开历史页面时偷偷生成全部纪要。

阶段 2 的预算出口应按模型绑定和实际序列化输入计算，而不是把“最多若干条总结”当作容量证明。请求准备需要为系统提示、问题、正文、来源引用、工具消息增长和输出额度留出空间；完整条目无法纳入时显式缩小证据集合或分批，不截断后宣称完整。没有受控 tokenizer 时继续用保守字节计数做规划；只有 provider 回执才能成为实际 token 用量。

内容验证建议用同一组合成来源和问题，对照三条路径：现有全文分块、仅总结检索、总结与原文共同检索。分别记录相关来源召回、引用是否能定位、日期/数量/否定/修订的答案依据、输入字节、实际请求数、已知 provider 用量与相对耗时；用量未知仍为 null。机械校验可以证明来源存在、版本正确和范围没有越权，不能证明引用语义支持每个结论，因此内容质量另以真实 provider 评估。

共享存储、contract、main/preload 与跨模块生命周期改动按 testing-strategy §2.1 扩大至相关 lane；PR 或阶段联合验收取得当前 revision 的完整三条 lane 证据。受控 provider 的确定性联合旅程不能代替真实 provider 质量、Windows 导航交互或其它实机验收。

本轮文档核查范围：CONTEXT 术语、相关 SEM/ADR/J 边界、当前代码路径、研究来源和本地相对链接。没有运行模型请求、产品测试或实机旅程；研究建议不改变现有能力的验收状态。
