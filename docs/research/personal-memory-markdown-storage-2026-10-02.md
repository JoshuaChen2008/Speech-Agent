# 个人记忆以 Markdown 存储的研究与讨论

检索日期：2026-10-02。本文基于公开第一方文档，属于研究建议，尚未形成架构决定；没有修改 SEM-F26/F30/F37 的已决定要求，没有迁移数据或修改产品代码。术语依据 [CONTEXT.md](../../CONTEXT.md)。

## 1. 研究结论

把用户需要长期查看、纠正和携带的个人记忆保存为 Markdown，有明确的第一方产品实践支持。它特别适合“脱离应用也能直接阅读、编辑”的需求。但这些资料不能证明 Markdown 在所有记忆场景都优于 SQLite，也不能证明更换文件格式就能提高检索质量。

本项目更值得讨论的方案是：**以 Markdown 保存已确认个人记忆的权威正文，以 SQLite 保留候选、来源、关联、撤销和运行记录；检索索引是可以从有效内容重新构建的派生数据。** 这是结合本项目约束提出的建议，不是外部产品对本项目的官方推荐。

必须区分三件事：

| 层次 | 回答的问题 | 建议边界 |
|---|---|---|
| 权威存储 | 用户的记忆究竟保存在哪里，修改哪一份才生效？ | 已确认个人记忆正文以受管理的 Markdown 为准；同一正文不允许数据库与文件分别独立修改 |
| 检索索引 | 如何快速找到相关条目？ | 可以使用本地索引，但索引不能把被撤销内容恢复为有效记忆 |
| 模型上下文 | 这次运行实际读到了什么？ | 仍由个人上下文模块按范围、有效性和预算生成个人上下文包，不把整个文件目录塞进每次模型请求 |

## 2. 官方材料中的实际做法

### OpenClaw：文本文件与 SQLite 配合

当前架构文档将记忆描述为普通文件加 SQLite 索引。长期内容与经历记录分层，来源信息保存为模型不能通过修改正文伪造的 SQLite 字段。它支持文件可编辑，但没有据此取消来源治理。[Memory architecture](https://docs.openclaw.ai/concepts/memory-architecture#provenance-every-memory-knows-where-it-came-from)

因此，“OpenClaw 用 Markdown”不能推导为“所有数据库内容均可删掉后仅凭 Markdown 无损恢复”。搜索缓存与来源、信任及撤销记录的恢复要求不同。这一点与本项目对来源修订和 suppression 的要求相关。

### Letta：Git 管理的 Markdown 记忆

当前 MemFS 文档描述 Git 仓库及 Markdown/YAML 文件；部分目录常驻模型上下文，其余按需读取。默认没有语义或向量索引，搜索扩展另行安装。提交用于版本管理与同步，单纯编辑本地工作文件不等于已经传播到所有运行环境。[MemFS](https://docs.letta.com/concepts/memfs)

这个案例说明，文件存储可以成为正式记忆架构，也说明文件、版本和上下文注入是不同机制。它没有直接解决本项目“用户确认、来源撤销和迟到响应不得恢复旧内容”的全部要求。

### Obsidian：本地 Markdown 加可重建缓存

官方文档明确说明，笔记是本地文件夹中的 Markdown，可以由外部编辑器修改；应用刷新这些变化。同时它使用 IndexedDB 保存元数据缓存，并提供失步后的重建方式。[How Obsidian stores data](https://help.obsidian.md/Files+and+folders/How+Obsidian+stores+data)

它支持用户对文件可编辑性的判断：开放文本格式便于人工掌控。但笔记软件的外部编辑体验并不自动等价于具有模型摄取、来源关联和撤销规则的个人记忆系统。

## 3. 可选方案与本项目取舍

| 方案 | 优点 | 代价 | 研究判断 |
|---|---|---|---|
| SQLite 权威，提供 Markdown 导出或编辑界面 | 现有事务、来源和修订链较容易保持 | 离开应用后编辑文件不能自然改变记忆 | 若主要问题是界面编辑体验，改动最小；不能满足“文件直接就是权威记忆”的完整意图 |
| Markdown 权威，治理记录与索引保留 SQLite | 用户直接阅读、编辑正文，同时保留来源和撤销控制 | 需要明确文件与数据库间的提交、失效和恢复协议 | 最符合本次用户诉求，优先讨论 |
| 仅使用 Markdown 和普通文件 | 文件目录可以独立携带全部数据 | 必须另行设计元数据、写入竞争、删除标记、恢复与索引；格式错误不能默默污染上下文 | 技术上可行，但不能把它视为低成本的后缀替换 |

以上取舍是工程推论，没有进行性能对照实验。尤其不能把“方便全文查找”与“自动理解同义表达”混为一谈：文本搜索、结构化过滤和语义检索解决不同问题。是否增加全文检索或向量检索，应独立依据真实问题与中文语料评估。

## 4. 建议的用户体验和内部约束

以下均为待讨论建议：

1. “我的记忆”仍是应用入口，同时提供“打开记忆文件夹”。个人记忆可按条目或项目拆成文件，避免所有内容塞入一个长期增长的大文件。
2. 文件正文由用户直接编辑；稳定条目 ID、范围等使用少量结构化元数据。来源引用、确认性质、撤销和修订不能仅靠可任意改写的 `confirmed: true` 之类字段决定。
3. 记忆候选与已确认个人记忆分开。自动模型输出先进入候选，不能通过写入某个文件夹直接升级为用户事实。
4. 外部编辑被检测后，按内容摘要建立新修订，并使依赖旧修订的个人记忆会话关联、记忆概览和缓存失效。后台任务提交前重新校验输入身份，不能覆盖外部编辑。
5. 程序写入前校验读入时的版本或摘要，冲突时保留用户修改并提示处理。文件监听只能作为发现变化的手段，启动、读取和提交边界还需要一致性检查。
6. 文件语法损坏、重复 ID、文件缺失和部分写入都要有明确反馈；不继续把过期索引当作当前有效记忆使用。
7. 删除文件是否等于“忘记”，需要明确产品语义。若等于忘记，应同步建立阻止旧来源再次摄取的 suppression，不能等下一次索引重建才失效。
8. “记忆概览”仍是可重建投影。直接修改概览不能被解释为已经修改每条底层个人记忆；若提供可编辑概览，必须明确怎样把修改落到底层条目。

外部编辑还存在身份边界：应用通常能发现文件发生变化，却不能仅凭文件内容证明是本人、同步程序还是其他 Agent 写入。需要在“用户明确指定并信任的编辑目录”与“导入文件形成候选”之间作出明确选择，而不是让导入文本自行声明其信任等级。

## 5. 隐私、携带与恢复

Markdown 是易读文本，SQLite 默认存储也不因其二进制容器而自动加密。使用哪种格式，都应明确文件夹权限、备份和云同步边界；不能因本地文件而承诺内容不会被其他软件读取。

若采用 Git 版本管理，修改和删除正文后，旧内容可能仍在历史、备份或同步副本中。Git 适合审阅差异，但“从当前记忆中移除”与“清除所有历史副本”必须分开说明。此处是对版本化存储的工程风险分析，不是要求本项目立即引入 Git。

仅复制 Markdown 可以携带可读的个人记忆正文；若要恢复原有来源、确认、撤销、关联及处理资格，必须同时携带受控治理记录，或明确定义导入为新候选。**可重建的是检索索引，不应把不可丢失的治理记录也叫缓存。**

## 6. 与现有语义的关系及后续讨论

[SEM-F26](../semantic-contract.md) 当前明确要求个人记忆和会话经历记录保存在现有 SQLite，并限制首版为结构化字段、规范化语义键及别名等值匹配；[SEM-F30/F37](../semantic-contract.md) 规定统一模块、有界个人上下文包及综合投影的撤销规则。因此，采用本研究方案之前，需要先修订相关语义行和 [J21/J22/J28、DB7](../testing-strategy.md)，再设计迁移与跨模块用户旅程。本文不替代该登记。

建议讨论时先决定三个产品问题：

- 用户希望直接编辑的范围，是已确认个人记忆，还是包括记忆候选与会话经历记录？
- 外部编辑保存后直接影响下一次运行，还是先在应用内展示差异并确认？
- 更优先的是“任何编辑器都能改”，还是“整个文件夹脱离本应用也能无损迁移全部治理语义”？后二者的实现成本不同。

本次仅核对公开文档、仓库术语、相关语义行、旅程与相对链接；未运行产品测试，未验证真实模型内容质量、文件监听或恢复行为。
