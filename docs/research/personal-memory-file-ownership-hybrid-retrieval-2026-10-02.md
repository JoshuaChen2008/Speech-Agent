# 用户拥有记忆文件与混合检索：研究建议

检索日期：2026-10-02。本文延续[存储研究](personal-memory-markdown-storage-2026-10-02.md)，以“文件属于用户、允许高度自定义”为目标。建议尚未形成架构决定，不修改 SEM-F26/F30/F37，也未实施检索或迁移。

## 1. 先保证用户拥有文件

建议用户选择个人记忆目录，以 Markdown 保存已确认个人记忆的权威正文；允许使用自己的编辑器、目录结构、文件名和标题。应用只约定最少的 frontmatter，例如稳定 `id` 与 `scope`；身份不绑定文件路径，所以重命名或移动不产生新记忆。用户不写元数据时，可以由应用协助补充，不能要求用户理解内部数据库结构。

未知的用户自定义字段应原样保留。自动处理不能重新排版整份文件、覆盖用户注释或强制目录模板。用户可以关闭 AI 写入权限而继续手动管理。模型生成的记忆候选与明确内容分开，程序修改明确内容前遵循既有确认规则。

文件所有权也应覆盖退出本应用的能力：正文可以直接携带；来源、修订与撤销信息应提供文档化的携带格式。SQLite 可以继续保留受控治理记录，但不能成为正文之外不可导出的锁定机制。复制文件只证明得到了这些文本，不能让导入文件自行声明“系统已经验证来源”。索引则始终可以删除并重建。

外部保存应被检测为新修订，旧关联与旧概览随即失效；程序提交前比较摘要，发生冲突保留用户修改。自由编辑不等于放弃来源和删除语义。这些都是本项目建议，需先登记再实施。

## 2. 两路检索值得做，但属于同一个 resolve

建议的目标结构是：在个人上下文模块的 `resolve` 内，先按授权、范围和生命周期限制候选，再进行词法与向量两路召回，融合、去重，最后复核当前版本并按预算返回个人上下文包。

| 检索方式 | 擅长的问题 | 可能的问题 |
|---|---|---|
| 词法检索，使用 BM25 排序 | 人名、项目名、缩写、编号、用户确切用词 | 换一种说法时可能漏掉 |
| 向量检索 | 同义表达、问法变化、自然语言意图 | 可能找来主题相似但本人、时间或项目不符的内容 |

Elastic 官方展示用 RRF 融合 BM25 与 kNN 结果；它根据排名组合，不要求两种原始分数采用相同量纲。可借鉴算法，不需要引入 Elasticsearch 服务。[RRF 官方说明](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

我的建议是将 RRF 作为简单基线，暂不引入独立向量服务、图检索或第二个重排模型。候选数量、融合参数和最终预算仍需评测；RRF 不保证召回率与准确率同时提高。召回更多相关条目时，也可能让干扰条目进入有限的上下文。

**检索相关性不能授予事实身份。** “接口项目”与“客户端项目”语义接近，可以用于查找背景，但不能证明那次会话中的发言属于用户；个人记忆会话关联仍按已确认信息及规范化字段、登记别名的等值匹配核验。

## 3. 中文词法检索要专门设计

SQLite FTS5 提供 BM25 和不同 tokenizer。其 trigram 全文查询不会匹配少于三个 Unicode 字符的子串，因此“预算”“偏好”等两字查询不能直接依赖该路径。该限制针对 trigram 全文查询，并不表示 SQLite 不能查找两字文本。[FTS5 trigram](https://www.sqlite.org/fts5.html#the_trigram_tokenizer)

建议中文词法基线独立评估分词或字符 n-gram，以及短词、标识符和原文子串的补充查找；不能把默认 tokenizer 当成中文质量证明。短词补充在有界有效条目集合中执行，记录成本，不静默扫描无限历史。

仓库的[会话问答检索](../../src/runtime/storage-worker/question-retrieval-store.js)已有临时 trigram 索引、BM25 候选与短词子串补充；最终又按词项命中排序。它可供借鉴，但不能据此宣称个人记忆已经具备混合检索。

向量侧可把 Qwen3-Embedding-0.6B 作为本地候选之一。官方发布中文检索评测，支持多语言与可调整表征维度；这些只证明具备候选资格，不证明它在本项目短记忆、中文简称或用户电脑上最优。[Qwen3 Embedding 官方材料](https://qwenlm.github.io/zh/blog/qwen3-embedding/)

## 4. 分阶段选择默认行为

**第一阶段**：建立文件权威、外部编辑、冲突和撤销流程；提供经过中文题集检验的词法检索。记忆数量较少时，有界读取与过滤可能已经足够，用户不应为了浏览和编辑记忆先下载表征模型。

**第二阶段**：用相同文件集合和题集比较词法、向量、RRF 三个方案。表征模型在本地生成索引；索引身份包含文件摘要、分块版本和模型身份，替换模型后重建。表征失败时显式回落词法，不影响文件管理和字幕系统。

少量核心明确偏好可以在预算内直接读取；日期范围和“全部事项”按结构化条件处理，不应全部依赖相关性排名。

建议先人工标注一组项目、偏好、简称、同义改写、两字查询、多义词和无答案问题，并加入已删、旧修订、休眠、错误项目和记忆候选等负例。在相同范围、返回条数和上下文预算下，比较 Recall@k、Precision@k、nDCG@k、无答案误召回率，同时记录延迟、内存、索引大小及更新成本。来源失效与越权内容进入上下文必须作为独立失败项。

只有向量带来稳定收益且成本可以接受时，才建议默认启用混合检索；否则保留为可选增强。不能凭公开榜单替代本项目验收，也不预先声称两路一定优于一路。

## 5. 与当前合同的关系

这是面向用户所有权的推荐方向：**文件权威、最少格式约束、治理可携带、检索可替换，一个个人上下文模块对外提供有界结果。**

[SEM-F26](../semantic-contract.md) 当前要求 SQLite 存储及等值匹配，故 Markdown 权威、词法和向量检索都属于待登记的语义变更；[SEM-F30/F37](../semantic-contract.md) 的模块边界、来源与撤销要求继续成立。若采纳，需先补 [J21/J22/J28、DB7](../testing-strategy.md) 的文件编辑、检索、撤销和故障旅程，再实施。

本次仅研究并核对术语、相关语义和链接，未运行产品测试或检索基准；模型、中文 tokenizer 和阈值均未定选。
