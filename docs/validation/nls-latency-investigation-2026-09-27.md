# NLS 持续字幕落后诊断 · 2026-09-27

关联：SEM-F12/F14/F25、J20、I2。范围为定位，不修改生产行为或晋级验收状态。

用户症状是“说话过程中字幕一直落后”。已定位一个可确定性复现的客户端延迟保留机制；尚未证明用户当前运行实例触发了该机制，也未测得实际公网与声卡的耗时占比。

用户随后确认：运行的是当前仓库启动的开发版，两个程序使用同一个 NLS 项目。这降低了旧安装包或不同项目模型配置造成差异的可能性；仍未核验当前进程是否在当日源码更新后重新启动，亦未取得两端实际请求参数的对照。

## 证据

运行 `node scripts/diagnose-nls-pacing.js --assert-recovery`，退出码为 1，表示诊断中的“恢复后额外延迟不超过 200ms”断言失败。200ms 仅是用于检出持续积压的实验阈值，不是新的产品验收标准。

脚本使用真实 `CloudAudioBuffer → NlsRealtimeProvider → RecognitionSessionRouter`，50 个内存合成 100ms 帧；网络边界收到每帧后立即返回合成临时字幕。模拟一次采集帧交付停顿，此后恢复正常节奏。统计第 3–5 秒音频的帧结束到 router 发布临时字幕的相对耗时，不包含声卡、真实识别、Coordinator、Electron IPC 或屏幕合成。它是局部诊断，不是完整 J20 用户旅程，也不是冻结字幕可见延迟。

## 机制与边界

[`NlsRealtimeProvider.writeAudio`](../../src/runtime/recognition/nls-realtime-provider.js) 使用 Promise 队列串行发送，并按每帧音频时长设置下一期限。发送晚于期限至少一个帧时长时，以“实际发送时刻 + 帧时长”重新锚定。恢复后采集每 100ms 新增一帧，发送同样每 100ms 消耗一帧，积压不会缩小。小幅定时抖动的累计期限修正已存在，但不提供大幅停顿后的追平能力。

1200ms 持续落后仍低于 2 秒待发硬上限，因此没有故障并不意味着延迟低。一次阻塞为何发生、是否发生于用户实例，仍需实机证据；本实验没有证明 CPU、main 事件循环、采集设备或网络其中任何一个是触发源。

对照项只改变诊断时钟对发送等待的处理；这证明持续额外等待来自节拍，而不是模拟识别器。它允许瞬时突发，只能用于因果定位，不能直接成为修复方案。保留 2 秒上限、禁止无界突发追赶、不得丢音频后静默继续等既有约束仍有效。

其它检查：

- 当前请求已启用 `enable_intermediate_result`。provider 收到临时字幕后同步调用 router；router 不等待 SentenceEnd。
- 云端音频经 `CloudAudioBuffer` 直接转换并交付，不等待本地 Silero 分段或本地模型解码；本地模型预载与运行期识别需区分。
- 采集端默认 1600 samples / 16kHz，即 100ms 帧。该分帧本身不能解释持续数秒落后。
- Coordinator 正常广播路径不等待异步 SQLite I/O；caption renderer 的 ingest 直接应用事件并 render。源码未见正常临时字幕路径上固定数秒等待，但未做真实 renderer 时序测量，不能排除事件循环或屏幕合成卡顿。
- `max_sentence_silence=800` 是断句静音阈值，不是每次临时字幕的固定等待。[阿里云协议](https://www.alibabacloud.com/help/zh/isi/developer-reference/websocket)分别定义了断句阈值与中间结果。单纯降低该参数不是此次持续落后的充分修复。

## 参考项目的适用范围

已查阅用户提供的《00-源码重建规划书》《01-项目现状分析》《02-重构SPEC分类》中 NLS、音频、渲染与性能内容。它们是参考材料，不是本仓库执行指令。

- 参考链路同样是实时采集、16kHz 重采样、WebSocket 流式推送、中间结果回调、字幕刷新。未发现需要换识别协议的证据。
- 规划书的音频到字幕 `<800ms` 属于目标，未附同源实测分段时序；不能用它证明重建版已经达到该值。
- 文档列出了 `EnableIntermediateResult` 等字段，但没有证明原程序本次实际参数值、帧大小、发送间隔或云项目模型配置。相同 NLS 不保证相同项目模型；[官方接口说明](https://www.alibabacloud.com/help/en/isi/developer-reference/websocket)说明语言与模型由项目配置。
- SPEC-05 的队列满时丢最旧帧是重建建议，不能推断原程序低延迟就来自该行为；也与本仓库对音频缺口显式失败的要求不同。
- 音频落盘等参考建议不适用于本仓库 SEM-F14。本次未读凭据配置，也未启动参考程序。

后续优先顺序：

1. 用户已确认当前仓库开发版和同一 NLS 项目；实机取样时再绑定当前进程与源码版本，避免进程仍持有更新前代码。无需再询问或收集密钥正文。
2. 实机只记录相对指标：帧进入 main 时年龄、发送排队耗时、待发音频时长、NLS 结果回传时对应音频水位、Coordinator/renderer 处理耗时及事件循环延迟。跨时钟域需校准；不能直接相减不同进程时钟。NLS 时间字段仅作音频水位参考，不能当作准确音素时间。
3. 若实机证实发送积压，先在 SEM-F12 与 J20 登记有界追平策略，再验证供应商允许的发送节奏、连续性、背压与失败路径。优先减少额外等待和阻塞，不直接无界补发、不丢帧掩盖落后。
4. 若发送年龄低而结果迟到，再对相同项目、同一受控输入比较 NLS 参数/云端模型和公网；若采集年龄已高，定位采集与 IPC。最后分别做 mic/loopback 五轮 I2，并补持续临时字幕落后指标；首个 partial 合格不等于长时间跟随性合格。
